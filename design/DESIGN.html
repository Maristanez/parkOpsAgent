1. Scope

D1 implements the validated domain model and the executable proposal path for the supplied fixture. StudentApplication.propose(String) reads booking B1, evaluates a target space under policy version 1, and stores a PENDING proposal that records the booking and policy versions it observed. The booking never moves; approval and execution are D2 work. bash run.sh run scripted demonstrates the accepted target B12 and the rejected targets D09 and Z99 using replayed input, which is not a live model run. 3. Design decisions and the alternatives rejected

Alternative considered: where the eligibility rule lives

The rule could have been an if inside StudentApplication.propose, or a method such as Space.isEligibleFor(Booking). It was placed in its own class, EligibilityPolicy, with its version number beside it. D3 replaces policy version 1 with version 2, which also requires an accessible target when the booking requires one, and must reject proposals created under the old version. With the rule and its version in one object, propose records policy.getVersion() in every proposal, D3 changes a single class, and D2's list-alternatives tool can reuse isEligible. An inline if would have mixed the rule with id generation and storage, and a method on Space would have made a space depend on a booking policy it should not know about.

DecisionAlternative rejectedReason
The status is the enum ProposalStatusA String statusA misspelt status cannot compile, and no status outside the brief's four can exist. toView() converts with status.name() because the supplied ProposalView stores a String.
Proposal's constructor always sets PENDING; no setterStatus as a constructor parameter, or a setStatus methodNo caller can create an already-approved proposal; the brief says approval never comes from the model. D2 will add controlled transitions that are legal only from PENDING.
Callers receive copies: snapshot maps and a list of ProposalView recordsReturning the Booking and Space objects or the internal List<Proposal>A caller cannot clear or add stored proposals, or later reach objects that D2 makes mutable (occupancy, proposal status). This is acceptance case D1-F.

4. Operation contracts

4.1 StudentApplication.propose(String targetId): ProposalView

  • Precondition: none beyond the call. targetId may be null, malformed or unknown; each case is handled.
  • Postcondition on success: targetId is a valid identifier, names a known space, and EligibilityPolicy.isEligible(booking, target) is true. A new Proposal is appended to the stored proposals with id "P" + n (n is the counter's previous value), booking id B1, target targetId, observed booking version equal to the booking's current version (0), observed policy version policy.getVersion() (1), and status PENDING. The method returns that proposal's ProposalView.
  • Postcondition on failure: throws IllegalArgumentException when targetId is malformed, unknown or ineligible.
  • Frame (what may change): only the proposal list (one append) and the id counter (+1), and only on success. The booking (its space, version and every other field), every Space and every existing proposal are unchanged in all cases.

4.2 EligibilityPolicy.isEligible(Booking booking, Space target): boolean

  • Precondition: booking and target are non-null; otherwise IllegalArgumentException.
  • Postcondition: returns true exactly when !target.getId().equals(booking.getSpaceId()), target.isOpen() and !target.isOccupied(). booking.requiresAccessible() does not affect the result under version 1. For the fixture, B12 and C03 are eligible; A17 and D09 are not.
  • Frame: changes nothing; it is a query.

5. Most important current limitation

A proposal stops at PENDING and nothing re-checks it. There is no operator approval, rejection or execution yet, so the observed booking and policy versions stored in each proposal are never compared with the current state, and a proposal that has gone stale cannot be detected. Every rejection is also the same IllegalArgumentException, distinguished only by its message. D2 must add the operator actions, revalidate versions and eligibility inside one sequential boundary before committing, and return distinct outcomes (NOT_APPROVED, STALE, UNAVAILABLE_OR_INELIGIBLE, COMMITTED, DUPLICATE).

Other limitations: one in-memory fixture with no persistence; a single sequential process, so no safety under concurrent access; and accessibility is deliberately ignored until policy version 2 in D3.

7. Testing

bash run.sh check runs the 14 supplied public checks as plain Java, and bash run.sh test runs 55 JUnit Jupiter tests: the same 14 checks, the infrastructure test and 40 student tests. All pass (results/d1.txt, 4 October 2026). Every rejection test asserts the unchanged booking, occupancy and proposal list after the exception, not only that an exception was thrown.
