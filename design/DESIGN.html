ParkOps D2: Design

EECS 3311 B, Fall 2026 · Deliverable 2: a working supervised agent · Route A (ParkOps) · Bryan Maristanez · November 2026

1. Scope

D2 turns D1's proposal path into a supervised agent for the supplied fixture. StudentApplication.run(ModelProvider, int) runs a bounded model/tool loop that can read booking B1, list eligible spaces and create one PENDING proposal, and then stops. Separate operator commands (approve, reject, execute) decide what happens next; execute re-checks the current state and either commits once or returns a named refusal. tick(long) detects bookings on closed spaces with caller-supplied time. Policy version 1 stays in force. bash run.sh run scripted demonstrates every path with replayed responses (not a live model run); bash run.sh run live uses the same loop with the supplied Ollama adapter. Figures 1–5 follow the text.

3. Proposal lifecycle

Figure 5 draws these transitions. execute checks, in order: the proposal exists and is for B1; already EXECUTED → DUPLICATE; not APPROVED → NOT_APPROVED; booking or policy version differs from the recorded one → STALE; target not eligible now → UNAVAILABLE_OR_INELIGIBLE. Only when all pass does commit occupy the target, release the old space, swap in the moved booking (version + 1), mark the proposal executed and append one commit and one notification. The checks and the commit run in one method with no model or external call in between; this is a sequential guarantee only, not safety under concurrent processes.

4. Two design decisions

4.1 The loop reaches the domain only through the application's public methods

Problem. The model's choices must never bypass a check that an operator call would go through, and must never be able to approve or execute. Decision. AgentRunner holds a StudentApplication and calls only its public methods (bookingSnapshot, alternatives, propose, policyVersion, spaceIds). The propose tool goes through the same propose that D1 tests, and its IllegalArgumentException becomes a tool error the model can react to. No approve or execute tool exists, and the parser rejects any extra property such as "approved":true, so the only path from a reply to a commit is a separate operator command. Alternative rejected: giving the runner the store and the domain objects directly. It would save a few methods, but every tool would need its own copy of the eligibility and version checks, and a bug there could change state the operator never saw. Enforcing the boundary in Java rather than in the system prompt is what the brief requires: the prompt describes the protocol, but nothing depends on the model obeying it.

4.2 Execution returns an outcome enum from one method that both checks and commits

Problem. Five results must be distinguishable, tests must assert them with unchanged state, and validation must not be separated from mutation. Decision. execute returns ExecutionOutcome and performs every check and the commit itself; commit is the only place a booking moves. Alternative rejected: one exception type per refusal (as D1's propose does). Refusals here are normal operator outcomes, not errors, so exceptions would make DUPLICATE look like a failure and would force callers into control flow by catch blocks. A separate canExecute query followed by commit was also rejected because it reopens the check-then-act gap. Unknown proposal ids remain IllegalArgumentException: that is a caller mistake, not an outcome.

5. Periodic detection and the conservative retry policy

tick(t) rejects a time below the previous tick with a clear IllegalArgumentException and changes nothing. The first tick scans; after that a scan happens on the first tick at or past each boundary of the 60-second grid that starts at the first tick (first + 60, first + 120, …), so a late tick does not shift later boundaries. A scan finds bookings on closed spaces and emits a WorkItem once per (booking, booking version, policy version), and not at all while a PENDING or APPROVED proposal exists for that pair; the agent likewise refuses to propose while such a proposal exists, so repeated work never issues a second active proposal for the same state. Ticks 0, 59 and 60 therefore give one item, then none (no scan), then none (scan, pair already emitted). Retry policy: once a pair has been emitted it is not emitted again on its own, even if the agent run failed (STEP_LIMIT, PROVIDER_ERROR) or the operator rejected the proposal. New work needs an explicit operator retry(bookingId) or a relevant version change (a changed booking or a new policy makes a new pair). This avoids a failing model being called again every minute for the same state, at the cost of a human having to notice and retry. tick never calls the model or proposes anything.

6. A rejected model/tool interaction

From run scripted step 7 (replay, not a live model): the first reply tries to grant itself authority. Java rejects it before any tool runs, counts it as an invalid response and tells the model why:

[assistant] {"tool":"PROPOSE_REASSIGNMENT","bookingId":"B1","targetId":"B12","approved":true}
[user] {"status":"REJECTED","reason":"unexpected property: approved"}

Nothing is proposed or approved. After six invalid replies the run ends with STEP_LIMIT after exactly six calls and no proposal. A valid request used wrongly is a tool error instead: proposing D09 returns TOOL_ERROR (“Target D09 is not eligible under policy version 1”), and if B1's version changes between the read and the list, the list returns TOOL_ERROR asking for a new READ_BOOKING. Tool errors use a call but are not counted as invalid.

8. Limitations

  • No live transcript yet. No course-supported endpoint was configured, so D2-N is recorded as LIVE_RUN_PENDING_COURSE_ACCESS. The live route was exercised only against a local fake endpoint during development; that is not a model run and is not reported as one.
  • Sequential and in memory. One process, one fixture, nothing survives a restart; the check-then-commit in execute is not safe under concurrent callers.
  • Policy version cannot change in D2, so only the booking-version half of STALE is exercised; D3's policy 2 will exercise the other half. Accessibility is still ignored, as policy 1 requires.
  • Work items are reported, not acted on. tick returns them; starting an agent run for one is left to the operator.
  • D1's propose still throws IllegalArgumentException for a bad target, because the supplied public checks expect it; the loop converts it into a tool error.

9. Reused infrastructure and corrections

Reused unchanged from the starter: ChatMessage, Fixture, MiniJson, ModelProvider, OllamaProvider, ProposalView, ReplayProvider, the build scripts, data/ and the supplied checks. Main keeps the starter's mode structure: scripted (and its alias agent-scripted) is now the D2 demonstration, scripted-d1 keeps the D1 regression demonstration, and live asks the operator before anything is approved.
